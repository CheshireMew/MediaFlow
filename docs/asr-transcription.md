# 本地转录的长音频处理

音频超过 15 分钟且开启语音活动检测（VAD）时，CLI 和内置引擎都使用语音分段批量推理。引擎按语音停顿组织不超过约 30 秒的识别片段；GPU 每批同时处理 4 段，CPU 每批处理 2 段，随后由引擎恢复原音频时间轴。应用不再将音频硬切成 10 分钟文件，也不依靠多个 Python 线程模拟模型并行。

所选模型保持不变，CUDA 明确使用 FP16。长音频加速不会自动切换 Turbo 或 INT8。CPU 延续原有 INT8 配置。用户明确关闭 VAD 时使用顺序识别，避免批量引擎擅自重新开启语音过滤。

显存或内存不足时，逐次减少批量大小（4 → 2 → 1），保持计算精度。CLI 每次重试使用独立输出目录，避免把失败后遗留的字幕当成成功输出。无法运行单段模型时报告失败；显存不足不会误报为驱动版本过低，也不会因此悄悄切到 CPU。只有已识别的 CUDA 运行环境错误继续沿用原来的 CPU 回退。

一个后端进程内，同一时间只允许一个转录任务持有模型运行权，任务内部使用批量并行。CLI 预热也遵守这一限制，防止同时加载多份大模型挤占显存。切换模型或引擎前释放之前缓存的模型。

CLI 同时输出 JSON 与 SRT，应用优先使用 JSON 里的逐词时间戳整理字幕，避免无标点中文被合并成几分钟一条。结果按时间排序，校正到原音频时长内；仅时间范围也相同的重复项才去重，保留说话者真实的重复表达。字幕写入成功后才报告完成。

如果某些识别片段没有逐词时间戳，或者 CLI 只有 SRT 输出，仍会拆分超长文字，并在日志中明确内部时间点是按文字估算的。转录页的“智能分割”会继续处理拆分后仍过长的段落，直到满足长度条件或受到最短时长、完整词语等限制；其它页面原有的单次拆分行为保持不变。已经生成的历史结果不会自动重写。旧 SRT 无法凭文字恢复准确逐词时间，需要精确对齐时应重新识别音频。

CLI 在模型加载或没有输出时也会检查暂停、取消请求，并终止、回收识别进程。控制检查不会重复发送相同的进度或反复写入数据库。内置引擎在识别片段返回时检查控制请求。恢复继续沿用转录步骤的 `replace_output` 策略，即重新执行当前转录步骤，不是从已识别片段断点续转。

批量分段会改变模型能够参考的前文，因此识别文字可能与顺序模式不同；保持 FP16 不代表两种模式的识别结果完全一致。当前默认用于长音频提速，尚不构成对逐字准确率的保证。

主要入口：`backend/services/asr/service.py`、`backend/core/asr_execution.py`、`backend/core/adapters/faster_whisper.py`、`backend/services/asr/core_strategies.py`。最低 faster-whisper 版本为已经验证的 1.2.1，锁文件原先已使用此版本。

2026-09-28 在 Windows、RTX 2080 Super Max-Q 8 GB 上，使用原播客第 10–26 分钟的连续 16 分钟音频验证：large-v2、CUDA FP16、自动识别语言、VAD 开启。顺序识别耗时 195.69 秒；批量 4 段耗时 83.25 秒，约为原速度的 2.35 倍。批量计时还包含约 7 秒的应用输入预处理，顺序计时从引擎启动开始；两者均包含模型加载。测试没有重跑整期播客，因此这个倍率不等于整期耗时保证。

实际测试确认暂停会退出识别进程且不发布部分结果；再次执行能完整输出到第 960 秒。对比两个输出，规范化文字长度为 5520 / 5542，未发现超过 18 字的连续插入、删除或替换，时间排序和边界检查通过。这里比较的是两种识别结果的一致性，没有人工逐字真值，不能据此计算识别准确率。
